# AWS infrastructure-as-code for Creatools (VPC, EC2, RDS, ALB, 3 domains)

Greenfield `infra/` directory adding a complete CloudFormation stack, multi-stage Dockerfile, Docker Compose, Nginx reverse proxy, and a bootstrap deploy script. The stack provisions a VPC with public/private subnets, an ALB with ACM wildcard certs across three domains (creatools.co, creatools.stream, creatools.live), a single EC2 instance running Docker, and an RDS PostgreSQL instance in private subnets. The user-data script clones the repo, builds the Docker image, writes a `.env` from CloudFormation parameters, and starts the app.

**Watch for:** User-data `.env` file gets leading whitespace on every line due to YAML heredoc indentation (confirmed). The Docker volume sharing model means Nginx serves stale frontend files on redeploy (confirmed). SSH is open to `0.0.0.0/0` (confirmed). The app has no host-based routing for the three domains — creatools.stream and creatools.live proxy everything to the same Express server which has no awareness of which domain served the request (confirmed). Storage migration from GCS/Replit to S3 is not implemented, so file uploads will fail (confirmed).

## High-level view

The CloudFormation template creates proper VPC isolation, NAT gateway, ALB with HTTP-to-HTTPS redirect, and DNS-validated ACM certificate across all three domains. Stack creation will block until nameservers propagate at the registrar — this is expected and documented but means the first deploy is not truly "one-click" without manual registrar intervention.

The Docker build uses a three-stage approach: build with pnpm, install runtime deps with npm into a flat `node_modules` (working around pnpm symlinks), then assemble a minimal production image. This is the right solution for the monorepo structure, but the Dockerfile silently falls back to `--no-frozen-lockfile` if the lockfile is stale, allowing non-reproducible builds.

The Nginx config splits traffic by `server_name` across three server blocks, but all three domains hit the same Express backend which doesn't inspect the `Host` header. The overlay and profile features are path-based (`/overlays`, `/profile`), not domain-based. Requests to `creatools.stream/overlay-id` or `creatools.live/username` will 404 because no routes exist at those paths in Express.

The deploy script and user-data have a heredoc indentation bug that will corrupt the `.env` file on first boot, making the app unable to connect to RDS or sign JWTs. This is the blocking issue.

## User-data `.env` heredoc indentation

The CloudFormation `UserData` uses `!Sub |` and the heredoc sits indented:

```yaml
          cat > infra/.env <<EOF
          NODE_ENV=production
          PORT=3000
          DATABASE_URL=postgresql://${DBUsername}:${DBPassword}@${RDSInstance.Endpoint.Address}:5432/creatools
          ...
          EOF
```

YAML literal block scalars strip the common leading whitespace. After YAML processing, bash receives the script with the `EOF` terminator at the same indentation as the content lines. Bash requires the terminator at column 0 (or uses `<<-EOF` with tabs). Because the terminator is space-indented, bash never closes the heredoc — everything after the `cat` command, including the health check loop, becomes part of the heredoc content written to `.env`. The deployment will appear to hang and the health check never runs.

Fix: replace with individual `echo "KEY=value" >> infra/.env` lines, or use a `printf` block.

## Docker volume sharing and frontend staleness

```yaml
services:
  api:
    volumes:
      - frontend_static:/app/public
  nginx:
    volumes:
      - frontend_static:/usr/share/nginx/html:ro
```

Docker named volumes copy data from the container's filesystem only on first creation. On redeploys (`docker compose up -d --build`), the existing volume is reused without updating its contents. The frontend will serve the version from the first-ever deploy indefinitely. The README's "update" section (`docker compose up -d --build`) won't actually update what Nginx serves.

Fix: use a bind mount to a host directory (e.g., `/opt/creatools/static`), or add `docker compose down -v` to the update flow (which also destroys other volumes).

## Security group SSH exposure

```yaml
EC2SecurityGroup:
  SecurityGroupIngress:
    - IpProtocol: tcp
      FromPort: 22
      ToPort: 22
      CidrIp: 0.0.0.0/0
```

For a production stack, this is an unnecessary attack surface. Add a `SSHAllowedCIDR` parameter defaulting to `0.0.0.0/0` with a description urging restriction, or better, add an IAM instance profile with `AmazonSSMManagedInstanceCore` policy and remove SSH entirely.

## Domain routing gap

Nginx separates the three domains:

- `creatools.co` — static frontend + `/api` proxy
- `creatools.stream` — full proxy to Express
- `creatools.live` — full proxy to Express

Express has routes mounted under `/api` only. For the secondary domains, a request to `creatools.stream/my-overlay` arrives at Express as `GET /my-overlay` — no route handles it. The same applies to `creatools.live/username`.

The application's overlay feature lives at `/overlays` in the SPA (frontend routes), and the API endpoints are at `/api/overlays/*`. For creatools.stream to serve overlay pages, Nginx should either:
- Serve the same SPA `index.html` for all paths (so the frontend router handles `/my-overlay`), or
- Rewrite incoming paths to match Express routes

Currently neither approach is implemented. The creatools.stream and creatools.live server blocks will return 502 or JSON error responses for any browser navigation.

## Database migration absent from bootstrap

The deploy script starts the app but never runs schema migrations. Drizzle ORM requires explicit `drizzle-kit push` or `drizzle-kit migrate` to create tables. The app's startup seeds (`seedDefaultPlans`) will fail silently (it catches errors), but any user-facing request hitting the DB will crash.

Add a migration step to the Dockerfile or deploy script:

```dockerfile
# In the builder stage, after build:
RUN npx drizzle-kit generate
# Or in deploy.sh, after compose up:
docker compose exec api npx drizzle-kit push
```

The migration tooling needs access to the Drizzle config and schema source, which aren't present in the production image. This needs architectural thought — either run migrations as a separate init container with the full source, or include the migration files in the production image.

## Dockerfile lockfile fallback

```dockerfile
RUN pnpm install --frozen-lockfile --config.confirmModulesPurge=false || \
    pnpm install --no-frozen-lockfile --config.confirmModulesPurge=false
```

If `pnpm-lock.yaml` is out of sync, the fallback silently resolves whatever is available. Two builds from the same commit could produce different `node_modules`. Remove the `||` fallback — a broken lockfile should break the build.
