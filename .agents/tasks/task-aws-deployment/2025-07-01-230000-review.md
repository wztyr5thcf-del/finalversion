# AWS deployment scaffold for Creatools monorepo

This change adds a complete `deploy/` directory (11 files, ~1400 lines) that provisions and deploys the Creatools pnpm monorepo (Express 5 API + React Vite SPA) to a single EC2 instance backed by RDS PostgreSQL. The approach is a classic single-server stack: AWS CLI scripts create infrastructure, a server-setup script installs the runtime, Nginx terminates TLS for three domains, PM2 runs the Node.js API in cluster mode, and a deploy script ties build-and-restart into one command.

**Watch for:** PM2's `env_file` option does not exist in PM2's configuration spec — environment variables will not reach the API process through this mechanism (confirmed). SSH is open to `0.0.0.0/0` by default in the provisioned security group (confirmed). The deploy script hardcodes `git pull origin main` with no mechanism for deploying a specific ref or rolling back a failed deploy (confirmed).

## High-level view

The provisioning script creates a standard single-AZ deployment: one EC2 instance, one RDS instance in the default VPC, security groups scoped so only the EC2 can reach the database. The script catches "already exists" errors for idempotency, but has no tear-down path or state tracking, so a partial failure leaves orphaned resources.

Nginx configuration is replicated three times — one server block per domain — serving the same root, same proxy, same headers. The three blocks differ only in `server_name` and certificate paths, creating a maintenance burden when shared settings change.

PM2 is configured for cluster mode with 2 workers. The `env_file` key in the ecosystem config is not a real PM2 option and will be silently ignored; the deploy script works around this by sourcing `.env` into the shell before calling `pm2 start`. But any out-of-band restart (manual `pm2 restart`, or `max_memory_restart` trigger) will lose those variables.

The SSL setup uses `certbot certonly --nginx` despite the Nginx config already having a `/.well-known/acme-challenge/` location block for webroot challenges — a mixed approach that would be cleaner as one or the other.

The backup script does not verify dump integrity after compression. A network interruption during `pg_dump` can produce a truncated file that `gzip` compresses without error.

## PM2 environment variable gap

The ecosystem config declares `env_file: '/opt/creatools/app/deploy/.env'` on line 19. PM2 does not support an `env_file` property; the documented options are `env` (an object) and per-environment blocks like `env_production`. The key is silently ignored at runtime.

The deploy path isn't broken because `deploy.sh` sources `.env` with `set -a` before calling `pm2 start` or `pm2 reload --update-env`. Variables reach PM2 through the parent shell. However, any out-of-band restart — `pm2 restart creatools-api` run manually, or a restart triggered by `max_memory_restart` — will lose the environment variables because PM2 persists only the `env` block from the ecosystem file, not the inherited shell environment.

The fix is either to move all required variables into the `env: {}` block (generated at deploy time from `.env`), or to wrap PM2's startup in a shell script that always sources `.env` first and is registered as the systemd unit's `ExecStart`.

## SSH security posture on provision

```bash
aws ec2 authorize-security-group-ingress \
    --group-id "$EC2_SG_ID" \
    --protocol tcp --port 22 --cidr 0.0.0.0/0
```

For a production deployment handling payment data (Stripe keys in `.env`), wide-open SSH is a meaningful gap between "works" and "secure by default." Accepting a `--ssh-cidr` flag or auto-detecting the caller's IP via `curl ifconfig.me` would close it at provision time rather than relying on a manual post-setup step.

## Deploy script fragility around build-time environment

`deploy.sh` sources `.env` (setting `PORT=8080` for the API runtime), then runs:

```bash
PORT=3000 BASE_PATH=/ pnpm --filter @workspace/creatools build
```

The inline overrides work because bash inline assignments take precedence. But this creates an implicit contract: the Vite config requires both `PORT` and `BASE_PATH`, the deploy script must know about both, and any new required env var in `vite.config.ts` must be added to this line. There's no validation step that checks the build-time contract is satisfied before the build runs.

## No rollback mechanism

The deploy script does `git pull origin main`, builds, copies assets, then `pm2 reload`. If the build succeeds but the new code crashes at startup, PM2's `max_restarts: 10` with `restart_delay: 4000` will keep retrying for ~40 seconds before giving up. At that point the app is down with no automated path back to the last working state.

A minimal improvement: tag the current commit before pulling, and on build or startup failure, `git checkout` the tag and re-deploy. Alternatively, keep the previous build artifacts in a timestamped directory and symlink-swap on success.

## Nginx configuration repetition

The three server blocks differ only in `server_name` and `ssl_certificate`/`ssl_certificate_key` paths. The 40+ lines of shared configuration (proxy settings, security headers, static asset caching, SPA fallback) are duplicated verbatim. When a change is needed — adding a CSP header, adjusting rate limiting — it must be applied in three places.

A `proxy-params.conf` and `security-headers.conf` included in each block would reduce the config to three ~15-line blocks plus shared fragments.
