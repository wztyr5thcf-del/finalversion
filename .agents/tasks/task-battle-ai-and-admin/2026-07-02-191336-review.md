# Battle AI feature, admin controls, and UI redesign

Three features landed together: a new Battle AI (BETA) system that models HeyGen Streaming Avatar sessions for TikTok lives, a full admin panel tab for managing it, and a dramatic visual overhaul across dashboard, sidebar, landing, and login pages. The backend uses a Drizzle schema with two tables (sessions + config), an Express CRUD layer, and a mock HeyGen integration path. The admin page gained four stub sections to fix pre-existing type errors, plus a complete Battle AI management panel. The UI redesign introduces glassmorphism utilities, neon glow animations, and particle-style background effects.

**Watch for:** HeyGen integration is entirely mocked even when `HEYGEN_API_KEY` is present (confirmed); RTMP URL is stored in plain text without validation or sanitization (confirmed); `JSON.parse` on user-controlled config fields can throw unhandled exceptions in the public config endpoint (confirmed); `makeId()` uses `Math.random` for primary keys (confirmed).

## High-level view

The Battle AI backend is a session-state-machine (idle -> streaming -> idle/error) persisted in Postgres via Drizzle, with a single-row config table governing feature flags and pricing. The HeyGen Streaming Avatar API is not actually called — both the key-present and key-absent code paths produce a mock session ID and flip status to "streaming," making the `/start` endpoint a state-bookkeeping no-op that presents itself to users as a real live stream activation.

The admin panel adds a `BattleAiAdminSection` with avatar CRUD, enable/disable toggle, pricing, plan restriction checkboxes, and a sessions table. The sessions table is read-only — no admin force-stop exists despite the UI implying control over active sessions. Four stub sections were added solely to unblock compilation.

The UI redesign is additive CSS (~120 lines of keyframes and utilities) and JSX restructuring. No structural component changes — the layout hierarchy is preserved, visuals are intensified. The dashboard hardcodes fake stat values (12470 followers, 892 gifts) that animate on mount — these will mislead users unless wired to real data.

<summary>Issues (7)</summary>

1. **HeyGen integration is dead code** — Even when `HEYGEN_API_KEY` is set, the `/start` endpoint produces a mock session ID and never calls the HeyGen API. Either implement the real call or remove the conditional branch to avoid false confidence that the integration works.
2. **RTMP URL stored without validation** — The RTMP URL arrives from the client and is persisted and (eventually) forwarded without any scheme/format validation. Validate `rtmp://` or `rtmps://` scheme at minimum.
3. **JSON.parse crash on malformed config** — `GET /battle-ai/config` calls `JSON.parse(config.availableAvatars)` and `JSON.parse(config.planRestrictions)` without try/catch. Malformed data crashes the endpoint with a 500.
4. **Math.random primary keys** — `makeId()` uses `Math.random().toString(36)` for session IDs. Collision probability is non-trivial at scale and the IDs are guessable. Use `crypto.randomUUID()` instead.
5. **No session timeout/cleanup** — A session stuck in "streaming" status (e.g., if the stop call never arrives) is never cleaned up. No background sweep or TTL exists.
6. **Admin force-stop route missing** — The admin panel's sessions table implies a force-stop capability, but no admin-level stop endpoint exists. Only the owning user can stop their session.
7. **Dashboard stat values are hardcoded** — The animated counters (12470 followers, 892 gifts, 34200 viewers, 94% engagement) are constants, not fetched from any API. Users will see fabricated numbers.

## HeyGen integration is a placeholder on both branches

The `/start` route checks for `HEYGEN_API_KEY` and branches, but both branches do the same thing: generate a mock ID and update the session to "streaming."

```typescript
// When key IS present — still a mock:
const mockHeygenSessionId = `heygen_${Date.now().toString(36)}`;
const updated = await updateSession(id, {
  status: "streaming",
  heygenSessionId: mockHeygenSessionId,
  startedAt: new Date().toISOString(),
});
res.json({ session: updated });
```

From a user perspective the button says "Entrar na Live" and the response gives no indication it's simulated when the key is configured. The frontend shows a green "Transmitindo ao vivo" badge regardless of whether anything was actually streamed.

## JSON.parse on public endpoint without error boundary

```typescript
res.json({
  enabled: config.enabled,
  availableAvatars: JSON.parse(config.availableAvatars),
  planRestrictions: JSON.parse(config.planRestrictions),
  ...
});
```

If `availableAvatars` or `planRestrictions` contains malformed JSON (empty string, corruption from a bad PUT), the entire request fails with an unhandled exception. The admin panel's `fetchConfig` wraps parse in try/catch, but the public endpoint does not — asymmetric error handling between admin write and public read paths.

## Session ownership and admin gap

The stop endpoint enforces `session.userId !== userId` — only the session creator can stop it. The admin sessions list (`GET /battle-ai/admin/sessions`) is read-only. There's no `POST /battle-ai/admin/sessions/:id/stop` for admin force-termination. If a user abandons a streaming session or the client crashes, no actor in the system can transition it back to idle.

## ID generation weakness

```typescript
function makeId(): string {
  return Math.random().toString(36).slice(2) + Date.now().toString(36);
}
```

`Math.random` is not cryptographically secure and produces ~52 bits of entropy. Combined with `Date.now` (predictable), this yields IDs that are guessable and collision-prone under concurrent writes. Session IDs appear in URLs (`/sessions/:id/start`, `/sessions/:id/stop`) making guessability a mild authorization concern since ownership is checked — but `crypto.randomUUID()` eliminates both risks trivially.

## RTMP URL as a credential

RTMP stream keys grant publish access to a user's TikTok live. The `rtmpUrl` field is accepted as a raw string with no scheme validation, stored in plain text, and returned in full on `GET /battle-ai/sessions`. The admin sessions endpoint also returns it — meaning any admin can see any user's stream key. If RTMP keys are considered credentials (they are), they should be treated with the same care as API keys: validate format, restrict who can read them, and consider encryption at rest.
