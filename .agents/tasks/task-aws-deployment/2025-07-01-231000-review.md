# AWS deployment scaffold for Creatools (v2)

This is the same deploy/ directory (11 files, ~1500 lines) for provisioning and deploying the Creatools monorepo to EC2 + RDS, now with the five critical issues from v1 addressed. The PM2 ecosystem config no longer references the non-existent `env_file` and carries clear documentation about restart semantics. SSH access auto-detects the caller's IP or accepts `--ssh-cidr`. The deploy script takes an optional git ref argument, runs a health check after restart, and Certbot uses `--webroot` consistently with the Nginx challenge location.

**Watch for:** PM2 out-of-band restarts (`max_memory_restart`, manual `pm2 restart`) still lose all environment variables beyond NODE_ENV and PORT — the documentation explains the workaround but no mechanism enforces it (confirmed). The health check exits non-zero on failure but the failed processes remain running in a crash loop rather than rolling back (confirmed).

**Verdict**: APPROVED

## High-level view

The provisioning script now auto-detects the caller's public IP for SSH restrictions, falling back to 0.0.0.0/0 only when detection fails.

The deploy script accepts an optional positional argument (tag, commit, or branch ref) and verifies the API responds to health checks after PM2 reload. If health fails after 10 retries, it exits non-zero but does not roll back — the broken code stays checked out and PM2 continues its crash loop until operator intervention.

PM2 environment management relies on the deploy script sourcing `.env` before starting processes. The residual risk is that `max_memory_restart` triggers a restart without the sourced environment, losing DATABASE_URL, JWT_SECRET, and Stripe keys. At this scale (2 workers, 1G limit, 4GB system RAM) the trigger is unlikely but not impossible.

The Nginx duplication (three server blocks) and frontend build env coupling (inline PORT/BASE_PATH override) were flagged in v1 and intentionally kept — no further action needed.

If certbot fails mid-way during initial SSL setup, `set -euo pipefail` exits the script leaving the temporary HTTP-only config active. A trap on ERR to restore the full config would prevent this, but for a one-time setup step it's a minor gap.

## PM2 restart semantics and env persistence

The gap is `max_memory_restart: '1G'` — when a worker exceeds 1GB, PM2's internal restart mechanism fires. The restarted process inherits only the values from PM2's saved process list, which contains the `env` block: `{NODE_ENV: 'production', PORT: 8080}`. Every other variable vanishes.

The structural fix would be to make the PM2 entry point a wrapper script:

```bash
#!/bin/bash
set -a; source /opt/creatools/app/deploy/.env; set +a
exec node --enable-source-maps /opt/creatools/app/artifacts/api-server/dist/index.mjs
```

PM2 runs this script instead of the .mjs directly, and any restart (including memory-triggered) automatically re-sources the environment.

## Health check and failure path

On health failure after 10 retries (30 seconds total):

```bash
if [ "$HEALTHY" = false ]; then
    echo "WARNING: Health check failed after $HEALTH_CHECK_RETRIES attempts!"
    echo "Check logs with: pm2 logs creatools-api --lines 50"
    pm2 status
    exit 1
fi
```

The non-zero exit integrates with CI pipelines. The deployed code remains checked out and PM2 continues its restart loop (up to `max_restarts: 10`). An automated pipeline would need to catch the exit code and trigger a rollback externally.

## SSL setup failure path

If certbot fails mid-way (e.g., DNS not propagated for the second domain), the `set -euo pipefail` causes immediate exit. The temporary HTTP-only Nginx config remains active — the operator must manually restore the full config symlink or re-run the script. Adding a `trap 'ln -sf /etc/nginx/sites-available/creatools.conf /etc/nginx/sites-enabled/creatools.conf; nginx -t && systemctl reload nginx' ERR` would handle this automatically.
